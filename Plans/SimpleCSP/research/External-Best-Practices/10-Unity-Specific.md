# 10 – Unity-Specific Practice

Engine mechanics that make or break CSP in Unity, followed by how the Unity netcode libraries approach prediction.

Legend: **[Consensus]**, **[Single-source]**, *(unverified)* as in [01](01-Time-and-Ticks.md).

---

## 1. FixedUpdate vs a custom tick loop

**Practice: drive the network tick from your own accumulator (in `Update` or a PlayerLoop entry) using unscaled time. Don't use `FixedUpdate` as the network tick.** [Consensus among netcode libraries]
- NfE, Fusion (`FixedUpdateNetwork`), FishNet (`TimeManager.OnTick`), PurrNet and Mirror-based prediction all run their own tick loop. PurrNet's `PredictionManager` "sets Unity physics to script mode per provider" ([PurrNet flow.md](https://github.com/PurrNet/PurrDocs/blob/main/client-side-prediction/flow.md)). FishNet's `TimeManager` can switch `Physics.simulationMode` to `Script` and call `Physics.Simulate(delta)` from its tick ([TimeManager.cs](https://github.com/FirstGearGames/FishNet/blob/main/Assets/FishNet/Runtime/Managing/Timing/TimeManager.cs)).
- *Why not `FixedUpdate`*:
  - its frequency depends on `Time.timeScale` ("How often MonoBehaviour.FixedUpdate is executed per frame depends on the timeScale"; at 0 it stops) ([Time.timeScale](https://docs.unity3d.com/ScriptReference/Time-timeScale));
  - its catch-up is capped by `Time.maximumDeltaTime`, so the sim silently loses time after hitches (§2);
  - you can't run it N extra times for replay, or skip/insert ticks for clock control;
  - it is not tied to a tick number.
- NfE explicitly separates the scaled sim delta from `UnscaledClientTime` for this reason ([time-synchronization.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/time-synchronization.md)).
- *When FixedUpdate is acceptable*: a prototype where the fixed rate equals the tick rate, `timeScale` is never changed, and replay calls your own `Tick()` directly rather than waiting for `FixedUpdate`.

```csharp
// Illustrative tick driver
void Update() {
    accumulator += Time.unscaledDeltaTime * clockScale;   // clockScale ~0.9-1.1 from time sync
    int steps = 0;
    while (accumulator >= Dt && steps < MaxTicksPerFrame) {
        RunTick(++localTick);            // poll input -> predict -> send
        accumulator -= Dt; steps++;
    }
    if (steps == MaxTicksPerFrame) accumulator = Mathf.Min(accumulator, Dt); // drop backlog
    float alpha = accumulator / Dt;      // for render interpolation (see 04)
}
```

## 2. `Time.maximumDeltaTime`, `Time.timeScale`, fixed step under hitches

- `Time.maximumDeltaTime` default **1/3 s**. After a 1 s hitch, `Time.deltaTime` reports 0.333 and `Time.time` advances only 0.333 s ([Unity manual: Handling variation in time](https://docs.unity3d.com/6000.3/Documentation/Manual/time-handling-variations.html)). The old Time Manager docs say it also limits physics/`FixedUpdate` work: physics "pretend[s] that frame took only Maximum Allowed Timestep seconds" ([Unity 4.5 Time Manager](https://docs.unity3d.com/450/Documentation/Manual/class-TimeManager.html)). So the most `FixedUpdate` catch-up steps per frame is about `maximumDeltaTime / fixedDeltaTime` (≈16 at 0.333/0.02) *(derived)*.
- **Consequence for netcode**: a long hitch makes Unity time fall behind real time. Using `Time.deltaTime`/`Time.time` for the network clock desyncs it. **Use `Time.unscaledDeltaTime` / `Time.realtimeSinceStartupAsDouble` for the network clock**, with your own catch-up cap and resync ([01 §5](01-Time-and-Ticks.md#5-recovering-from-hitches-and-large-desync)). [Consensus: NfE `UnscaledClientTime`, PurrNet `Time.unscaledDeltaTime` for views ([flow.md](https://github.com/PurrNet/PurrDocs/blob/main/client-side-prediction/flow.md))]
- **Mirror's time note**: keep network time as `double`. As a `float` it loses precision: "after 1 day, accuracy goes down to 8 ms … after 10 days … 62 ms" ([time-sync.md](https://github.com/MirrorNetworking/MirrorDocs/blob/main/manual/guides/time-sync.md)). Prefer integer ticks for simulation and `double` only for wall-clock estimates. [Single-source but uncontroversial]
- `Time.timeScale` changes apply "on the following frames", and `fixedDeltaTime` is not scaled in recent versions ([Time.timeScale](https://docs.unity3d.com/ScriptReference/Time-timeScale)). Keep slow-motion/pause effects out of the network sim, or make them part of the predicted state.

## 3. Running the simulation multiple times per frame (replay)

**Practice: `Tick(in Input, ref State, float dt)` must be a plain function you can call any number of times in one frame. It reads only its arguments and explicitly-restored state, and writes only state.** [Consensus]
- PurrNet: "Do not change a Unity component during simulation without ensuring the corresponding state captures and restores that change" ([best-practices.md](https://github.com/PurrNet/PurrDocs/blob/main/client-side-prediction/best-practices.md)). NfE: the processing system "can be called multiple times per tick, as previous ticks (rollbacks) are handled" ([command-stream.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/command-stream.md)).
- **Unity components with hidden state are the trap**:
  - `CharacterController.isGrounded`/`collisionFlags` update only on `Move`.
  - Rigidbody velocities change in `Physics.Simulate`.
  - Animator state, `Transform` children, and coroutines.
  - netfox hits the same with Godot's `CharacterBody` (`is_on_floor()` only updates after a move), and works around it with a zero-velocity move before checking ([rollback-caveats.md](https://github.com/foxssake/netfox/blob/main/docs/netfox/tutorials/rollback-caveats.md)). The equivalent in Unity is to compute grounded yourself (sphere/capsule cast) and store it in state *(adaptation)*.
- **Collision queries during replay see the *present* world** for non-predicted objects. This is the "holding the rest of the world fixed" assumption ([Gaffer](https://gafferongames.com/post/what_every_programmer_needs_to_know_about_game_networking/)). It's fine for static level geometry and is the reason moving platforms need special handling ([07 §5](07-Weapons-and-Predicted-Gameplay.md#5-predicted-player-vs-non-predicted--remote-objects)).

## 4. CharacterController vs Rigidbody vs kinematic movement

| Option | Under prediction | Notes |
|---|---|---|
| **Custom kinematic controller** (capsule casts / `Physics.ComputePenetration` on a kinematic body or no body) | Best fit [Consensus among FPS-focused stacks] | Fully deterministic given state, replay-safe, no `Physics.Simulate` needed. The Fusion KCC addon is this approach ([KCC overview](https://doc.photonengine.com/fusion/v2/addons/advanced-kcc/overview)) |
| **`CharacterController`** | Workable with care | `Move()` is immediate and replay-friendly. But setting `transform.position` is overridden by its internal position unless you disable/enable it or call `Physics.SyncTransforms()` ([Unity forum](https://forum.unity.com/threads/character-controller-ignores-transform-position.617107/), [issue tracker](https://issuetracker-mig.prd.it.unity3d.com/issues/charactercontroller-overrides-objects-position-when-teleporting-with-transform-dot-position)). FishNet's demo: "It is VERY important to disable the CharacterController component before updating its position … the physics for the CharacterController will remain at it's prior position until the next simulate" ([FishNet CharacterControllerPrediction.cs](https://github.com/FirstGearGames/FishNet/blob/main/Assets/FishNet/Demos/Prediction/CharacterController/Scripts/CharacterControllerPrediction.cs)). `isGrounded` is only refreshed by `Move` |
| **Dynamic `Rigidbody`** | Expensive / fragile | Replay needs `Physics.Simulate` (whole scene or a separate scene) per replayed tick. PhysX isn't bit-deterministic across machines (§6). Mirror and Fusion document the cost ([Mirror CSP doc](https://github.com/MirrorNetworking/MirrorDocs/blob/main/manual/general/client-side-prediction.md), [Fusion physics addon](https://doc.photonengine.com/fusion/v2/addons/physics-addon-2.0)). FishNet offers `PredictionRigidbody` to make forces replay-safe ([PredictionRigidbody docs](https://fish-networking.gitbook.io/docs/guides/features/prediction/predictionrigidbody)) |

**Recommendation for a 16–32p FPS**: a kinematic character (custom or `CharacterController` with the disable/enable or `SyncTransforms` rule). Keep dynamic rigidbodies out of the predicted set ([07 §5](07-Weapons-and-Predicted-Gameplay.md#5-predicted-player-vs-non-predicted--remote-objects)).

## 5. `Physics.Simulate`, `simulationMode`, `SyncTransforms`, physics scenes

- **Manual stepping**: set `Physics.simulationMode = SimulationMode.Script` and call `Physics.Simulate(fixedStep)`. "If you pass framerate-dependent step values (such as Time.deltaTime) … your simulation will be non-deterministic". `FixedUpdate` is still called at `fixedDeltaTime` regardless ([Physics.Simulate](https://docs.unity3d.com/ScriptReference/Physics.Simulate.html), [manual simulation](https://docs.unity3d.com/2022.3/Documentation/Manual/physics-optimization-cpu-manual-simulation.html)).
- **Separate physics scenes**: `PhysicsScene.Simulate` steps only that scene. Create one with `LocalPhysicsMode.Physics3D` ([PhysicsScene.Simulate](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/PhysicsScene.Simulate.html)). Some resimulation designs use this to replay a small predicted subset without stepping the whole world *(the design pattern is unverified as a cited practice; the API is documented)*.
- **Transform sync**: `Physics.autoSyncTransforms` is **off by default** and recommended off. When off, transform changes reach physics only before the simulation step. "If you modify a Rigidbody or a Collider component's transform values directly and then immediately need to perform a physics query … manually call `Physics.SyncTransforms` before the query" ([autoSyncTransforms](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Physics-autoSyncTransforms.html), [transform sync manual](https://docs.unity3d.com/6000.3/Documentation/Manual/physics-optimization-cpu-transform-sync.html)).
  - **In replay**: after restoring state (setting transforms) and before the first replayed tick's queries, call `Physics.SyncTransforms()`. FishNet exposes `OnPre/PostPhysicsTransformSync` events around its post-reconcile sync ([PredictionManager.cs](https://github.com/FirstGearGames/FishNet/blob/main/Assets/FishNet/Runtime/Managing/Prediction/PredictionManager.cs)). [Consensus]
  - **For lag compensation** that moves real colliders: sync after rewinding and after restoring ([06 §4](06-Lag-Compensation-and-Hit-Registration.md#4-hitboxes-vs-colliders-history)).
- **NfE's equivalent**: physics runs in `PredictedFixedStepSimulationSystemGroup`, "called multiple times up to the required number of predicted ticks". It warns about the spiral of death when physics re-simulates many ticks ([physics.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/physics.md)).

## 6. Float determinism limits (Mono vs IL2CPP, platforms)

- **CSP does not need bit-exact determinism**, only close agreement over the replay window. Server corrections fix drift. NfE: "It isn't necessary for the simulation itself to be fully deterministic, although this is something you should aim for … the client's state becoming *eventually consistent*", and "Fundamentally, Netcode is not a deterministic package" ([intro-to-prediction.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/intro-to-prediction.md), [prediction-details.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/prediction-details.md)). Gaffer 2004 says the same ([Networked Physics 2004](https://gafferongames.com/post/networked_physics_2004/)). [Consensus]
- **What *is* known**:
  - Gaffer: floats can be deterministic "provided you use an executable built with the same compiler, run on machines with the same architecture, and perform some platform-specific tricks". Expecting identical results across compilers/architectures "or even … debug and release builds" is "incredibly naive" ([Floating Point Determinism](https://gafferongames.com/post/floating_point_determinism/)).
  - PhysX in Unity: "Enhanced Determinism" makes simulation consistent "provided that the game inserts the actors in a deterministic order", at a performance cost ([Physics settings](https://docs.unity3d.com/2023.2/Documentation/Manual/class-PhysicsManager.html)). Forum reports say it is deterministic on the same machine/build but not across CPU vendors or x86 vs ARM ([Unity forum](https://discussions.unity.com/t/determinism-physx/866457)).
  - Unity Physics (DOTS) is designed to be deterministic ([com.unity.physics docs](https://github.com/needle-mirror/com.unity.physics/blob/master/Documentation~/index.md)).
  - Mono vs IL2CPP: only forum-level evidence. IL2CPP compiles to C++ with the platform compiler, so results depend on it, and engine math may use SIMD paths you don't control ([Unity forum](https://discussions.unity.com/t/are-floats-cross-architecture-deterministic-il2cpp-unity-2020-lts/850114), [GameDev.net](https://gamedev.net/forums/topic/708301-floating-point-determinism-in-unity-physx-and-net-intel-vs-amd/5432335/)).
- **Practical rules**:
  1. Server and clients may differ in backend/CPU. Expect tiny float drift and size tolerances accordingly ([03 §2](03-Reconciliation-and-Replay.md#2-always-replay-vs-compare-then-replay-with-a-tolerance)).
  2. Keep the operation order identical (same code path for tick and replay).
  3. Quantise predicted state at end of tick on both sides if you quantise it on the wire ([03 §3](03-Reconciliation-and-Replay.md#3-what-state-to-store-and-compare)).
  4. Fixed-point or `sfloat` is only needed for lockstep/rollback-of-everything designs (PurrNet `DeterministicIdentity`, Quantum) ([PurrNet best-practices](https://github.com/PurrNet/PurrDocs/blob/main/client-side-prediction/best-practices.md)). That is **overkill** here.

## 7. GC and allocation: struct ring buffers

**Practice: fixed-size arrays of structs indexed by `tick % N` for inputs, predicted states and lag-comp history. No per-tick allocations, no LINQ, no boxing in the tick path.** [Consensus by example]
- Source uses `m_pCommands[sequence_number % MULTIPLAYER_BACKUP]` ([in_main.cpp](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/in_main.cpp)); Q3 uses `CMD_BACKUP` masks ([cg_predict.c](https://github.com/id-Software/Quake-III-Arena/blob/master/code/cgame/cg_predict.c)).
- Mirror's prediction code notes "SortedList foreach iteration allocates a LOT. use for-int instead" ([Prediction.cs](https://github.com/MirrorNetworking/Mirror/blob/master/Assets/Mirror/Core/Prediction/Prediction.cs)).
- PurrNet: "PurrDiction copies and disposes states frequently. Use … disposable collections for variable-sized state … implement `IEquatable<T>` … when equality checks would otherwise be expensive" ([best-practices.md](https://github.com/PurrNet/PurrDocs/blob/main/client-side-prediction/best-practices.md)).
- Keep input/state structs blittable (no managed references) so copies are memcpy-cheap and comparisons can be field-wise. Store tick numbers in each slot and check `slot.Tick == wanted` to detect overwritten entries *(standard ring-buffer practice)*.
- Size: `N ≥ max replay ticks + redundancy window + safety`. NfE uses 64 ticks for the input queue ([prediction-details.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/prediction-details.md)), and UE uses 96 saved moves ([CMC code copy](https://gist.github.com/NoirMorilec/1ebe1a6f742c193101265a928b90c897)).

## 8. Animation and Animator under prediction

**Practice: keep the Animator *out* of the predicted simulation. Drive it from presented (interpolated/smoothed) state and local input in the view layer, and never let animation affect gameplay state unless that animation state is itself in the predicted state.** [Consensus]
- Fusion: "Unity's Animator cannot be rewound and re-simulated, so it cannot be relied on for tick-accurate animations". Tick-accurate animation requires "the complete animation state must be part of the networked data" ([Network Mecanim Animator](https://doc.photonengine.com/fusion/v2/manual/sync-components/network-mecanim-animator), [Fusion animation](https://doc.photonengine.com/fusion/v2/concepts-and-patterns/animation), via search).
- Manual evaluation exists (`Animator.Update(dt)`, or a paused `PlayableGraph` evaluated manually). Unity warns it "might not work well with the physics engine or any other system that is normally evaluated by the Game loop" ([Animator.Update](https://docs.unity3d.com/2018.2/Documentation/ScriptReference/Animator.Update.html), [forum on PlayableGraph](https://discussions.unity.com/t/animator-update-has-no-effect/865744)). That is too heavy for a simple system.
- **Gameplay timings come from state, not animation events**: reload completes at `reloadEndTick`, not on an `AnimationEvent`, and fire timing is the tick. Animations are then scaled to match. Root motion should be avoided for predicted characters *(general; consistent with the sources above)*.
- **Server hitboxes** need *some* pose. Use stance-driven capsules, or server-side animation of a simplified rig ([06 §4](06-Lag-Compensation-and-Hit-Registration.md#4-hitboxes-vs-colliders-history)). A forum report found animation-driven hitboxes broke determinism in a replay system, likely because of SIMD in Unity's animation code ([Unity forum](https://discussions.unity.com/t/are-floating-point-numbers-deterministic-on-the-same-architecture-il2cpp/892251)). [Single-source]

## 9. Script execution order, host / listen-server mode

- **Order within a tick must be identical on client and server**: (1) apply input, (2) movement, (3) weapon, (4) post-move queries, (5) save state. Do this by calling your systems explicitly from one tick driver, not by relying on `MonoBehaviour.Update` order. `[DefaultExecutionOrder]` only orders lifecycle events, and Unity says it doesn't guarantee order for events that "can happen at any time" ([DefaultExecutionOrder](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/defaultexecutionorder)). NfE's tracing tool lists "differences in system update order between the client and the server" as a misprediction cause ([prediction-tracing-tool.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/testing/prediction-tracing-tool.md)). [Consensus]
- **Host / listen server**:
  - The host's own player is authoritative (no prediction or reconcile needed). It still needs **render interpolation between ticks**. NfE single-world host mode: "Partial ticks aren't supported on hosts. Instead, interpolate your ghosts between full ticks" ([single-world-host-mode.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/single-world-host-mode.md)).
  - Remote clients' players on the host are server-simulated. They advance when their inputs are consumed, so the host sees them with whatever buffer the input path has. Host smoothing settings differ (UE `ListenServerNetworkSimulatedSmoothLocationTime` 0.04 s vs 0.1 s) ([CMC code copy](https://gist.github.com/NoirMorilec/1ebe1a6f742c193101265a928b90c897)).
  - "Binary worlds" host (a client world + server world in one process) keeps parity with dedicated servers at extra CPU. "Single world" is cheaper but runs different code paths ([single-world-host-mode.md](https://github.com/needle-mirror/com.unity.netcode/blob/master/Documentation~/single-world-host-mode.md)).
  - Code that gates on `isServer`/`isClient` must handle both being true. NGO suggests writing logic against "authoritative/non-authoritative" instead ([dealing-with-latency.md](https://github.com/Unity-Technologies/com.unity.multiplayer.docs/blob/main/docs/learn/dealing-with-latency.md)).
  - PurrNet: "Test as a remote client, not only as host" ([best-practices.md](https://github.com/PurrNet/PurrDocs/blob/main/client-side-prediction/best-practices.md)).
  - Host advantage (sees remotes with no network delay) and host cheating are inherent ([08 §9](08-Bandwidth-Messaging-AntiCheat.md#9-host--listen-server-caveat)).
